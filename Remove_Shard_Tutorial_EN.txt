======================================================================
REMOVE A SHARD FROM THE LAB SHARDED CLUSTER (MongoDB 8.3 or later)
Lab built with setup-sharded-lab-en.sh - removing shard3RS
======================================================================

Based on: Remove Shards from a Sharded Cluster (MongoDB Manual 8.3+)
https://www.mongodb.com/docs/manual/tutorial/remove-shards-from-cluster/

----------------------------------------------------------------------
0. LAB CONTEXT
----------------------------------------------------------------------
Cluster created by the script:

  Router (mongos) .... localhost:27017
  Config servers ..... cfgRS     (27101-27103)
  Shard 1 ............ shard1RS  (27201-27203)
  Shard 2 ............ shard2RS  (27301-27303)
  Shard 3 ............ shard3RS  (27401-27403)   <-- the shard we remove
  Admin user ......... clusterAdmin
  Test collection .... labdb.customers (shard key { _id: "hashed" })

With less than 15 GB of RAM the script uses 1 member per replica set,
so shard3RS only has sh3-a (port 27401). With 3 members it also has
sh3-b and sh3-c.

Goal: move every piece of data off shard3RS onto shard1RS and
shard2RS, then remove shard3RS from the cluster without losing data.

----------------------------------------------------------------------
1. WHAT TO KNOW BEFORE YOU START
----------------------------------------------------------------------
- You must migrate the shard's data to the remaining shards before
  removing it.
- Do not create, shard, or move collections while you run this
  procedure. It can cause interruptions and unexpected results.
- Do not use this procedure to migrate a whole cluster to new
  hardware. There is a separate procedure for that.
- Removing a shard can close open change stream cursors, and they
  may not be fully resumable.
- You can safely restart the cluster during the removal. Draining
  continues automatically after the components restart.
- MongoDB records the draining status in the config.shards
  collection.
- If you need to remove several shards, start draining all of them
  at the same time instead of one by one. A shard can only take part
  in one chunk migration at a time. Here we remove only one;
  section 12 shows how it would work with several.
- Collections stored entirely on the shard are moved with
  moveCollection. Review the moveCollection considerations and
  requirements in the manual before you start.

----------------------------------------------------------------------
2. CONNECT TO THE MONGOS AND CHECK THE STARTING STATE
----------------------------------------------------------------------
Always work through the mongos (port 27017), never directly on a
shard.

  mongosh --port 27017 -u clusterAdmin -p --authenticationDatabase admin

Note how the data is distributed now, so you can compare later:

  use labdb
  db.customers.countDocuments()          // expected: 30000
  db.customers.getShardDistribution()    // about 33% on each shard
  sh.status()

----------------------------------------------------------------------
3. STEP 1 - MAKE SURE THE BALANCER IS ENABLED
----------------------------------------------------------------------
The balancer moves the chunks off the shard, so it must be enabled.

  sh.getBalancerState()

  true  -> enabled, continue.
  false -> enable it:

  sh.startBalancer()
  sh.getBalancerState()                  // must return true

----------------------------------------------------------------------
4. STEP 2 - CONFIRM THE NAME OF THE SHARD
----------------------------------------------------------------------
  db.adminCommand({ listShards: 1 }).shards.map(s => s._id + "  " + s.host)

The shards._id field is the shard name. In this lab it is:

  shard3RS

----------------------------------------------------------------------
5. STEP 3 - START DRAINING THE SHARD
----------------------------------------------------------------------
This starts moving chunks of the sharded collections (for example
labdb.customers) from shard3RS to the other shards:

  db.adminCommand({ startShardDraining: "shard3RS" })

----------------------------------------------------------------------
6. STEP 4 - CHECK THE STATUS AND MOVE UNSHARDED COLLECTIONS
----------------------------------------------------------------------
Check the draining status:

  db.adminCommand({ shardDrainingStatus: "shard3RS" })

Typical output while it is still running:

  {
    msg: "draining ongoing",
    state: "ongoing",
    remaining: { chunks: ..., dbs: ..., jumboChunks: ..., collectionsToMove: ... },
    shard: "shard3RS",
    note: "you need to call moveCollection for collectionsToMove and
           afterwards movePrimary for the dbsToMove",
    dbsToMove: [ ... ],
    collectionsToMove: [ ... ],
    ok: 1
  }

What to look at:
- remaining.chunks: chunks the balancer still has to migrate. It
  drops on its own.
- collectionsToMove: collections stored entirely on shard3RS
  (unsharded collections, or collections of a database whose primary
  shard is shard3RS). The balancer does NOT move these. You must move
  each one yourself.
- dbsToMove: databases whose primary shard is shard3RS. See step 5.

If collectionsToMove is not empty, move each collection. Example:

  db.adminCommand({
    moveCollection: "labdb.mycollection",
    toShard: "shard1RS"
  })

In a lab built only with the script, collectionsToMove is usually
empty, because labdb.customers is sharded. If you created extra
collections without sharding them (for example in the shard key
exercises), they can appear here.

Optional - watch the draining until it finishes (stop with Ctrl+C):

  while (true) {
    const s = db.adminCommand({ shardDrainingStatus: "shard3RS" });
    printjson({ state: s.state, remaining: s.remaining,
                dbsToMove: s.dbsToMove, collectionsToMove: s.collectionsToMove });
    if (s.state === "drainingComplete") break;
    sleep(5000);
  }

----------------------------------------------------------------------
7. STEP 5 - MOVE PRIMARY SHARDS (dbsToMove)
----------------------------------------------------------------------
Each database has a primary shard. If shard3RS is the primary shard
of a database, that database appears in dbsToMove.

Do this AFTER collectionsToMove is empty, as the status note says.

  db.adminCommand({ shardDrainingStatus: "shard3RS" }).dbsToMove

For each database in the list, for example labdb:

  db.adminCommand({ movePrimary: "labdb", to: "shard1RS" })

Whether labdb appears here depends on which shard MongoDB picked as
its primary when it was created. You can check it with:

  db.getSiblingDB("config").databases.find({}, { primary: 1 })

----------------------------------------------------------------------
8. STEP 6 - CONFIRM DRAINING IS COMPLETE AND REMOVE THE SHARD
----------------------------------------------------------------------
  db.adminCommand({ shardDrainingStatus: "shard3RS" })

Wait until you see:

  { msg: "draining completed successfully", state: "drainingComplete", ok: 1 }

Then remove the shard:

  db.adminCommand({ commitShardRemoval: "shard3RS" })

Expected result: { ok: 1, ... }
If the shard is not fully drained, the command returns an error.
Go back to step 4.

----------------------------------------------------------------------
9. VERIFY THE RESULT
----------------------------------------------------------------------
  db.adminCommand({ listShards: 1 }).shards.map(s => s._id)
  // expected: [ 'shard1RS', 'shard2RS' ]

  use labdb
  db.customers.countDocuments()          // must still be 30000
  db.customers.getShardDistribution()    // now only shard1RS and shard2RS
  sh.status()

----------------------------------------------------------------------
10. STEP 7 (OPTIONAL) - REDISTRIBUTE THE DATA WITH reshardCollection
----------------------------------------------------------------------
After you remove shard3RS, the chunks that left that shard stay
wherever the balancer put them. To spread labdb.customers evenly
across the remaining shards, rewrite the collection with the same
shard key by using forceRedistribution.

Before you start:
- You can reshard only one collection at a time.
- You need free disk space of about twice the size of the
  collection.
- Resharding takes AT LEAST 5 minutes, even for a small collection.
  With 30000 documents, about 5-6 minutes is normal.
- mongosh shows nothing while the command runs. That is why you
  follow the progress from a second terminal (step 8).

10.1 Stop the balancer (terminal 1, connected to the mongos):

  sh.stopBalancer()
  sh.getBalancerState()                  // must return false

10.2 Run the resharding (terminal 1):

  db.adminCommand({
    reshardCollection: "labdb.customers",
    key: { _id: "hashed" },
    forceRedistribution: true
  })

The command waits until it finishes. Do NOT close this terminal.
Expected result at the end: { ok: 1, ... }

To cancel it (the collection stays as it was before):

  sh.abortReshardCollection("labdb.customers")

----------------------------------------------------------------------
11. STEP 8 - FOLLOW THE PROGRESS WITH THE reshard_progress.js SCRIPT
----------------------------------------------------------------------
The script queries $currentOp every 10 seconds. For each shard that
receives data (recipient) it shows the percentage of documents
copied, the percentage of time, the time elapsed, and the time left.
It stops on its own when the resharding finishes.

11.1 Create the script (terminal 2, in Linux, not in mongosh).
     Copy from the "cat" line through the "EOF" line, inclusive:

cat > ~/reshard_progress.js <<'EOF'
const NS = "labdb.customers";
const INTERVAL_MS = 10000;   // refresh every 10 s

function num(x) {
  if (x === undefined || x === null) return null;
  return typeof x.toNumber === "function" ? x.toNumber() : Number(x);
}

function bar(pct, width = 30) {
  const p = Math.max(0, Math.min(100, pct));
  const full = Math.round((p / 100) * width);
  return "[" + "#".repeat(full) + "-".repeat(width - full) + "] " + p.toFixed(1).padStart(5) + "%";
}

function fmt(sec) {
  if (sec === null || sec < 0) return "calculating...";
  const m = Math.floor(sec / 60), s = Math.round(sec % 60);
  return `~${m}m ${String(s).padStart(2, "0")}s`;
}

while (true) {
  const ops = db.getSiblingDB("admin").aggregate([
    { $currentOp: { allUsers: true, localOps: false } },
    { $match: { type: "op", "originatingCommand.reshardCollection": NS } }
  ]).toArray();

  if (ops.length === 0) {
    print(`\n[OK] No active resharding for ${NS}. It finished (or has not started).`);
    break;
  }

  print(`\n=== Resharding ${NS} - ${new Date().toLocaleTimeString()} ===`);

  ops.filter(o => (o.desc || "").includes("Recipient")).forEach(o => {
    const elapsed  = num(o.totalOperationTimeElapsedSecs) ?? 0;
    const left     = num(o.remainingOperationTimeEstimatedSecs);
    const docsTot  = num(o.approxDocumentsToCopy) ?? 0;
    const docsCop  = num(o.documentsCopied) ?? 0;
    const pctDocs  = docsTot > 0 ? (docsCop / docsTot) * 100 : 0;
    const pctTime  = (left !== null && left >= 0) ? (elapsed / (elapsed + left)) * 100 : 0;

    print(`\n${o.shard}   state: ${o.recipientState ?? "n/a"}`);
    print(`  Documents ${bar(pctDocs)}  (${docsCop} / ${docsTot})`);
    print(`  Time      ${bar(pctTime)}  elapsed ${fmt(elapsed).replace("~", "")} | left ${fmt(left)}`);
  });

  const c = ops.find(o => (o.desc || "").includes("Coordinator"));
  if (c) print(`\nCoordinator: ${c.coordinatorState ?? "n/a"}`);

  sleep(INTERVAL_MS);
}
EOF

11.2 Run the script (terminal 2):

  mongosh --port 27017 -u clusterAdmin -p --authenticationDatabase admin --file ~/reshard_progress.js

  Or, if you are already inside mongosh:

  load("/home/<your_user>/reshard_progress.js")

  To stop it before it finishes: Ctrl+C.

11.3 How to read the output. Example:

  === Resharding labdb.customers - 10:42:15 ===

  shard2RS   state: applying
    Documents [##############################] 100.0%  (15012 / 15000)
    Time      [###############---------------]  50.7%  elapsed 4m 02s | left ~3m 55s

- Each shard appears twice in $currentOp, as donor and as recipient.
  With forceRedistribution every shard both sends and receives data.
  The script shows only the recipients, because that is where the
  document counters are.
- Documents: documentsCopied / approxDocumentsToCopy. The total is an
  estimate, so it can go slightly above 100%.
- Time: elapsed / (elapsed + left). At the start the remaining time
  is -1 and the script shows "calculating...". The estimate is
  usually higher than the real time.
- With 30000 documents the copy reaches 100% almost right away and
  the state changes from cloning to applying. The operation keeps
  running until the 5-minute minimum, so the Time bar is the best
  indicator of how much is left.

11.4 When it finishes (the script prints [OK] and terminal 1 shows
     { ok: 1 }), turn the balancer back on and verify:

  sh.startBalancer()
  sh.getBalancerState()                  // must return true

  use labdb
  db.customers.countDocuments()          // must still be 30000
  db.customers.getShardDistribution()    // ~50% on shard1RS and ~50% on shard2RS

12. REFERENCE - REMOVING SEVERAL SHARDS IN PARALLEL (DO NOT RUN)
----------------------------------------------------------------------
In this lab we only remove shard3RS, so this section is for
reference only. It shows how you would remove several shards.

Why in parallel instead of one by one:
- If you remove one shard at a time, the balancer can move its data
  onto another shard that you plan to remove later. That data is
  migrated twice.
- A shard can only take part in one chunk migration at a time. If
  you drain several shards together, more migrations run at the
  same time and the process finishes sooner.

Example: a cluster with 4 shards (shard1RS to shard4RS) where you
want to remove shard3RS and shard4RS. Collections and databases
always move to a shard that stays (shard1RS or shard2RS), never to
another shard that is draining.

1) Start draining every shard before you go on:

  const toRemove = ["shard3RS", "shard4RS"];
  toRemove.forEach(s => printjson(db.adminCommand({ startShardDraining: s })));

2) Check the status of each one:

  toRemove.forEach(s => {
    const r = db.adminCommand({ shardDrainingStatus: s });
    printjson({ shard: s, state: r.state, remaining: r.remaining,
                dbsToMove: r.dbsToMove, collectionsToMove: r.collectionsToMove });
  });

3) For each shard, first move what appears in collectionsToMove
   (moveCollection) and then what appears in dbsToMove
   (movePrimary), as in steps 4 and 5. The destination is always a
   shard that stays:

  db.adminCommand({ moveCollection: "<db>.<coll>", toShard: "shard1RS" })
  db.adminCommand({ movePrimary: "<db>", to: "shard2RS" })

4) When ALL of them show state: "drainingComplete", remove them:

  toRemove.forEach(s => printjson(db.adminCommand({ commitShardRemoval: s })));

5) Check with listShards that only shard1RS and shard2RS remain, and
   clean up the Linux services of each removed shard, as in
   section 13.

----------------------------------------------------------------------
13. CLEAN UP THE LINUX SIDE (LAB)
----------------------------------------------------------------------
The shard3RS processes keep running until you stop them. They are no
longer part of the cluster.

Run these in the Linux terminal, not in mongosh.

1 member per replica set (your 7 GB lab):

  sudo systemctl disable --now mongod-lab@sh3-a

3 members per replica set:

  sudo systemctl disable --now mongod-lab@sh3-a mongod-lab@sh3-b mongod-lab@sh3-c

Optional - delete the data of the removed shard (DESTRUCTIVE):

  sudo rm -rf /data/mongo/sh3-*

Notes about the lab script:
- "status" still lists sh3-* and will show them as inactive. This is
  expected.
- "start" still starts sh3-*, because the script always expects
  3 shards. The process runs on its own and the cluster does not use
  it. Stop it again with the systemctl command above.
- "reset" still removes everything correctly.

----------------------------------------------------------------------
14. OPTIONAL - ADD shard3RS BACK (RETURN TO 3 SHARDS)
----------------------------------------------------------------------
Use this to repeat the exercise in class. Start with an empty data
directory. The example uses 1 member (port 27401).

In the Linux terminal:

  sudo systemctl stop mongod-lab@sh3-a
  sudo rm -rf /data/mongo/sh3-a/*
  sudo systemctl enable --now mongod-lab@sh3-a

Initialize the replica set (there are no users yet, so the localhost
exception lets you connect without credentials):

  mongosh --port 27401 --eval '
    rs.initiate({ _id: "shard3RS", members: [ { _id: 0, host: "localhost:27401" } ] })'

Optional - create the shard-local administrator again:

  mongosh "mongodb://localhost:27401/admin?replicaSet=shard3RS"

Then run:

  db.getSiblingDB("admin").createUser({
    user: "shardAdmin",
    pwd: passwordPrompt(),
    roles: [ { role: "userAdminAnyDatabase", db: "admin" },
             { role: "clusterAdmin", db: "admin" } ]
  })
  exit

From the mongos, as clusterAdmin:

  sh.addShard("shard3RS/localhost:27401")
  db.adminCommand({ listShards: 1 }).shards.map(s => s._id)

The balancer only moves data back to shard3RS when the difference
between shards reaches its migration threshold. With the small lab
data set, labdb.customers may stay on shard1RS and shard2RS.
To spread it across all 3 shards right away, repeat steps 7 and 8
(sections 10 and 11). Expected: about 33% on each shard.

With 3 members: wipe /data/mongo/sh3-a, sh3-b and sh3-c, start all
three units, and use the three hosts (27401, 27402, 27403) in
rs.initiate() and sh.addShard().

----------------------------------------------------------------------
15. QUICK TROUBLESHOOTING
----------------------------------------------------------------------
- remaining.chunks does not go down
    The balancer is off -> sh.getBalancerState() / sh.startBalancer().
- jumboChunks > 0
    Some chunks are too big to migrate. See "Clear jumbo Flag" in the
    manual.
- collectionsToMove is not empty
    The balancer does not move them. Run moveCollection for each one.
- dbsToMove is not empty
    Run movePrimary for each database.
- commitShardRemoval returns an error
    The shard is not fully drained. Check shardDrainingStatus again.
- Unauthorized
    Connect with -u clusterAdmin -p --authenticationDatabase admin.
- reshardCollection looks frozen
    This is normal: it takes at least 5 minutes. Follow the
    progress with reshard_progress.js (section 11). To cancel:
    sh.abortReshardCollection("labdb.customers").
- The script prints [OK] but never showed progress
    The resharding had not started or had already finished. Check
    that NS in the script is "labdb.customers".
